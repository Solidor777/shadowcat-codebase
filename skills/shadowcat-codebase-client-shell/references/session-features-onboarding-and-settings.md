# Session features, onboarding tours, route prefix, settings sections

AppContext and WorldSession seams for presence, profiles, module status, portals, pause, plus the onboarding tour contract, the route-prefix rule and the settings sections. Read it before adding an AppContext member, a settings section, a tour or a client fetch.

## New AppContext members need fixtures

Every member below must also be supplied by `SurfaceHarness`, `setAppContextForTest` and any hand-built context, or a test that mounts a component reading it crashes: `presence`, `memberProfiles`, `moduleStatus`, `activeModuleManifests`, `portal`, `bars`, `stageView`, `notes.present`, `notifyProgress`, `placeEffect`. A mocked `ServerConfig` must carry `onboarding_enabled` (the schema requires it).

## Members

- `AppContext.presence` (`SvelteMap` user -> online) is fed by the out-of-band `Presence` frame (`WorldSession.presence`) and re-seeded by every `Welcome`: `WorldSession.#onWelcome` clears the map and sets each `online_users` entry true synchronously before its first await, so a later transition frame lands on top of the snapshot and a reconnect drops stale entries. After the roster read lands, a listed member with no entry is set offline; an entry a frame created during that await is kept. A member with no entry at all is unknown (no dot). The `Presence` component draws online/offline/unknown dots, the member's colour (glyph chosen by luminance) and avatar.
- `AppContext.memberProfiles` / `MemberProfile` come from the roster (`WorldMember` colour, pronouns, `has_avatar`); `avatarUrl` is world-scoped and takes an optional `version` appended as `?v=`. The roster read seeds the map on each `Welcome`, and `WsClientHandlers.onMemberProfile` (the `MemberProfile` frame) updates one member live: `WorldSession` builds the avatar URL with a per-session counter as `version` so an image element re-requests the new bytes, and deletes the entry when the frame carries no colour, pronouns or avatar. `onMemberProfile` also upserts `members` (the frame carries `username`), so a member seated mid-session appears at once; it sets presence offline only when the member has no entry, so an existing online entry is kept. `ProfileEditor` (colour, pronouns, avatar upload/preview/remove through `updateProfile`, `uploadAvatar`, `deleteAvatar`) is mounted in `Settings.svelte`; `MessageCard` colours the author.
- `AppContext.moduleStatus` (`SvelteMap`, fed by ONE `WorldSession` reporter fed from `ModuleRegistry.activate`'s outcomes, first-party modules included, keyed by folder id; a failure also raises a toast) and `AppContext.activeModuleManifests`. `ModuleManager` shows status lines, disables the checkbox of a module that is engine-incompatible AND not yet enabled (`InstalledModuleInfo.engine_compat_ok`, server-computed, fail closed; the client never recomputes the semver match), and runs `checkSatisfiability(candidateIds, catalog, running)` before Save, which disables Save on issues. An already-enabled module that has become incompatible keeps an active checkbox so the GM can switch it off; blocking it would leave the world unable to save, because the server rejects a batch that still names it. The client check is advisory; the server decides.
- `AppContext.portal` (`onOffer`, `choose`, `decline`, `open`) and `PortalChooser` mounted in `Table.svelte` (it registers with `escapeCoordinator` only while an offer shows: the compact modal at `ESCAPE_PRIORITY.MODAL`, the wide non-blocking card at the lowest band, `ESCAPE_PRIORITY.TOOL`, so an Escape aimed at an open menu wins over it); see `shadowcat-codebase-scene-rendering`. `AppContext.placeEffect` sends a module placement; the server answers failure with an error frame and success with silence. `AppContext.stageView` is written by `Stage`; the chat-bubbles module reads it through `STAGE_OVERLAY_CONTRACT`. `AppContext.bars` carries the resolved bars. `AppContext.notes.present` sends `PresentNote` (the `NoteSheet` Present button shares a private note first); `Table.svelte` hosts `createPresentedNoteHandler`.
- Session pause: `resolveSessionPause` / `sessionFreezes` drive the topbar `SessionPauseBanner`, `PauseControls` (GM toggle through `promptDialog`, an `Alt+KeyP` binding, a pause-audio checkbox), the combat tracker's frozen header, rows, add and reorder, and `ToolContext.movesFrozen`. Buttons are not disabled; selection, doors and emotes keep working. In the compact size class `PauseControls` shrinks its toggle and audio checkbox (smaller font, capped widths, wrapping text) so the row's non-shrinking items, the settings entry included, stay on screen.
- Chat-history recall: `chat-history` (`CHAT_HISTORY_LIMIT`, `CHAT_HISTORY_BYTE_BUDGET`, `pushChatHistory`, `parseChatHistory`) persists per world under `UiState.worlds[id].chatHistory` through `sessionState` (per-key dirty tracking); the byte budget keeps the whole `ui_state` under the server's 64 KiB cap (`MAX_UI_STATE_BYTES`), so a new `ui_state` key must budget against that cap. `Composer` ArrowUp/ArrowDown recall restores the draft.
- `getUiState` / `putUiState` / `UiState` live in core `user-rest` (the shell re-exports them); module settings use `ui_state.modules` and `ModuleContext.settings` (`getWorld`/`setWorld`/`getUser`/`setUser`). `setWorld` resolves on dispatch; a server capability rejection arrives through the normal rejected-intent rollback. The core knows no theme: theme is a shell concern.
- Combat tracker: a `defeated` toggle on `CombatantRow` (gated on can-edit or the resource-edit cap), group stripes and the add-combatants picker. Combat editors use `SettingPath` `combat.expiryNotice`; a new setting path needs a `resolveSettingProvenance` case.
- `ConditionTogglePalette`, `TagChips`, `EffectsList`: see references/interaction-primitives.md.

## Route prefix

The server can serve the app under a path prefix, so NO client code may write a bare same-origin `/api`, `/modules` or `/ws` literal. Build every same-origin URL with `apiPath` / `wsUrl` (core `base-path`; `basePath` is the only reader of the prefix global). The shell page carries a base-href placeholder and the import map is relative (`./runtime`); a module entry URL goes through `apiPath` in `WorldSession`'s entry builder. `pnpm lint:route-prefix` enforces it (literals are allowed only inside `apiPath` calls and error messages). `lint:comments` and the route-prefix Playwright project (a prefixed server on a port above the base) ride the same convention.

## Onboarding tours

- Contract (core `tour`): `TOUR_CONTRACT`, `TourMeta` / `TourStep` (strict schema, `validateTourMeta`; `labelKey` required), `TOUR_ANCHOR_ATTR` (`data-tour`). A step targets an anchor ID (`isTourAnchorId`), never a selector. A contribution declares `tour` and/or `tourAnchor`; `ContributionRegistry.contribute` validates both; `Surface` wraps a `tourAnchor` contribution in a `display: contents` wrapper carrying the attribute, and `findTourAnchor` returns that wrapper's first element child.
- The `onboarding` module: `TourController` (one offer per session; eligibility by audience, first use, done-version and a mounted step), progress as flat keys under `ui_state.modules.onboarding` (`g:`/`w:` prefixes and a disabled flag) through `ctx.settings.setUser`, `TourOffer` toast (Take Tour / Not Now / Disable Tutorials: Not Now records the offered tour done, Disable Tutorials marks every registered tour done and switches offers off, and `TourController.howTo` / `TourHint` follow every answer), `TourOverlay` (spotlight, card, compact bottom sheet, Escape, focus trap, reduced motion), `OnboardingHost` as an overlay surface, `ReplaySection` as its own settings section. `serverFlag` parses `/api/config` with `ServerConfigSchema`; only an explicit false suppresses. `--statusbar-height` is a theme token (in the ui-kit token list, default `2rem`, declared with the shell's layout metrics) that sizes the `Layout` status bar grid row; `TourOffer` and `TourHint` anchor their bottom edge to it, so changing the token moves them with the row.
- First-party tours declare anchors in their own modules (scene-tools, stage, actors, chat, chat-composer dice, notes, settings, scene-browser). Tours for panels that can be closed are MANUAL (replay only), because an anchor that is not mounted cannot be spotlighted. The scene-browser tour (`sceneBrowserTour`, audience `gm`, contributed under `scene-browser:tour`) sets its `data-tour` attributes directly in `SceneBrowserPanel` rather than through `Contribution.tourAnchor`: panel root, list, create button, and an actions anchor on the FIRST row only (`i === 0`), so with no scene that anchor is unmounted and the step is skipped. The tour contract has no `requires`. The entry module's `Welcome` view shows after setup when onboarding is enabled.

## Settings sections

- `SettingsSectionMeta.serverAdminOnly` hides a section from non-admins (also self-gated). Sections: `settings:backups` (`BackupManager`: Back up now, Restore and Delete behind `ConfirmDialog`, retention line, failed-restore banner with an admin Dismiss through `dismissRestoreFailed`, actions locked while the server is stopping), `TrashManager` (cursor list, Load more, a refresh on `TrashEntryGoneError`; its empty-all `confirmDialog` passes `messageParams: { n: entries.length }` and uses `settings.trash.emptyConfirmMore` instead of `settings.trash.emptyConfirm` while `hasMore` is true, because the count is then a lower bound), `settings:port-forward` (`PortForwardSection`: admin-only, toggle disabled when the config locks it, the external address is admin-only), `ChangePasswordForm` (every user; a 429 maps to `settings.account.tooManyAttempts`; success logs out).
- Backup, trash and port-map REST wrappers live in core (`adminBackup`, `backup-rest`, `trash-rest`, `portmap-rest`, `format.ts` `fmtBytes`) because a module cannot import the shell; a settings module imports them from `@shadowcat/core`.
- `GameSettingsPanel` writes OCC settings: facing vision and turn rule, auto-rotate, scene padding margin, blind-roll toggles, vision treatment kind and parameters. The treatment kinds a module registers on `VISION_TREATMENT_CONTRACT` come from `ContributionRegistry`, which is not reactive, so the panel reads it through a `createSubscriber` bridge over `ctx.contributions.subscribe`; a plain read would never show a treatment registered while the panel is open.
- The `onboarding` Playwright project is the only e2e server with onboarding on: it has no seeded admin (setup runs through the UI) and omits `SHADOWCAT_ONBOARDING_ENABLED`, while every other project's server sets it to `false` (`SERVER_ENV` in `playwright.config.ts`). Only `onboarding.spec.ts` (`ONBOARDING_SPEC`) runs there.
