# Chat: audience commands, audience revision, secrets, flavor, extensions, notes presenting

Orientation for the chat features layered on the send pipeline. Read it before touching `chat::parse_command`, `resolve_audience_intent`, `handle_revise_audience`, `Segment::Secret`, roll flavor, the opaque `system` payload, the chat-card extension contract, the composer history, chat bubbles or the present-note relay.

## Audience commands and the revision door

- `chat::parse_command` is pure. It records an `AudienceIntent` (`Whisper`, `GmOnly`, `Public`, `Blind`, `SelfOnly`, `Players`, `ReplyToLastWhisper`) and a `MessageKind`; it never reads the repository. Tokens: `/w`, `/gm`, `/gmroll`, `/publicroll`, `/blindroll`|`/br`, `/selfroll`|`/sr`, `/players`, `/reply`, plus the display-only `/ooc` (`MessageKind::Ooc`) and `/ic` (`MessageKind::Normal`), which carry no intent.
- `resolve_audience_intent` is the ONE resolver, run by `handle_send_message` whether the intent came from a frame field or a content command; `validate_audience` then runs on its result. `/players` resolves to a whisper roster of every current non-GM member frozen at send time. `/reply` reads `Repository::last_whisper_to` (a JSON-array membership lookup of the sender's most recent received whisper) and fails with `SendMessageError::NoReplyTarget` when there is none.
- An edit never changes who reads a message: `handle_edit_message` rejects any audience command in the edited text with `SendMessageError::AudienceLocked`. The one door that changes readership after send is `ClientMsg::ReviseAudience` -> `handle_revise_audience`.
- `handle_revise_audience` checks, in order: GM world role (else `Forbidden`), the shared rate bucket, the message exists, is a `message` doc of a world scope and is not a tombstone (`NotFound` otherwise), `validate_audience`, `readers_for_audience`, `permissions_for_audience` and `validate_blind_content`. It then stores the new `Audience` and writes ONE `Operation::Update` of five `FieldChange`s (the `/engine` body plus the four `SMR_PERMISSION_PATHS`) under `WriteOrigin::ServerMessageRevision`. `message_property_overrides` runs AFTER the new audience is stored on the engine, because it reads the audience to decide whether rolls hide their results. `permissions_for_audience` is given the author id, so the author's `DocRole::Owner` entry survives every revision.
- The data-layer admission that lets this write through is `SMR_PERMISSION_PATHS` / `SMR_READERSHIP_PATHS` in `data::sqlite` (see `shadowcat-codebase-documents-permissions`). The readership trio is admitted only for a GM author, so the GM-only rule holds even for a caller that reaches `apply_intent` directly.

## Secret spans

- Authoring grammar: `[[secret:gm|...]]` and `[[secret:@name @name|...]]`. `chat::body::Composer::secret_visibility` resolves the spec through `rolls::parse_secret_spec`: `gm` -> `Visibility::GmOnly`; named users -> `Visibility::Recipients` holding those users plus the author. The inner body composes recursively into `Segment::Secret { visibility, content }`, sharing the ONE span budget (`Composer.spans_left`, bounded by `rolls::MAX_INLINE_ROLLS`) across every nesting level; `RollError::SecretTooDeep`, `MalformedSecret`, `UnknownSecretRecipient` and `TooManySecretRecipients` are the refusals.
- Hiding is by `permissions.property_overrides`, never by a client check. `segment_property_overrides(root, content)` registers each secret's `{path}/content` AND `{path}/visibility` under the secret's own tier (a `Recipients` value names its users, so the ids go only where the content goes), recursing into nested content so a roll inside a secret is classified at its full path. One walk serves messages (`/engine/content`) and notes (`/engine/body`), so the two document types cannot disagree on what a segment hides.
- `message_property_overrides` is the complete override set of a stored message: `roll_property_overrides` plus `/engine/source` restricted to the author when the content holds a top-level secret (`has_secret`), and `/engine/source` GM-only on a blind message with a roll. EVERY site that writes a message's `permissions.property_overrides` goes through it, so the set matches the content it protects (create, edit, recalc, revise).
- A viewer excluded by the tier receives a `Segment::Secret` whose `visibility` and `content` keys were removed by egress. Both fields carry `#[serde(default)]`; the default visibility is `GmOnly` (`withheld_secret_visibility`), so a stripped copy never reads as broader than it is. `Recipients` id lists inside `property_overrides` are emptied for a viewer they do not name (`data::permission::scrub_recipient_lists` for deltas, `filter_properties` for whole documents); see `shadowcat-codebase-documents-permissions`.
- `chat::body::compose_static` (a note's synchronous body composer) accepts only `[[secret:gm|...]]`; a `@name` spec is `RollError::SecretRequiresGm` because resolving a username needs the repository.

## Roll flavor and link labels

- `Segment::RollEmbed` and `Segment::RollButton` carry an optional `flavor`. A `/roll formula | flavor` body splits at its FIRST `|` through `rolls::split_roll_flavor` (the dice grammar has no `|` token); the formula is trimmed, the flavor is `None` when empty. The inline span `[[roll:formula|label|flavor]]` splits through `split_button_span` (first `|` ends the formula, second ends the label). Flavor is searchable text, player-visible, survives recalculation and is rendered escaped (never `{@html}`); a roll button's click resends its flavor.
- `Segment::DocLink.label` is optional. An authored label always wins; a label-less link resolves its text live from `ctx.documents` (`SegmentList`'s `docLinkText`, subscribed through `createSubscriber`), and a target whose name is `null` renders a placeholder because the name is redacted for that viewer. A `doc:`/`token:` span whose `|` tail is empty is `RollError::MalformedDocLink`.

## Sanitizer: fragment-only links

`chat::sanitize` allows a same-page link whose URL is `#` plus one or more of `A-Za-z0-9_-` (`fragment_only_url`, installed as ammonia's relative-URL evaluator for every policy). Every other schemeless form (`//host`, `host/path`, `/path`, a fragment with other characters) loses the attribute. The `<img src>` collector stays absolute-URL only, so a fragment never queues an inline-image job. The note table of contents (`sheet-note`'s `collectHeadings`/`findAnchor`) and in-note scrolling depend on this.

## The opaque `system` payload and chat-card extensions

- `ClientMsg::SendMessage` may carry `system`: an opaque, module-owned JSON value stored verbatim as the message document's `system` band (`MessageDraft.system`; `{}` when absent). It passes the same `validate_system_size` cap as any document's system band and is readable by exactly the audience that reads the message. The server never interprets it. Edit does not touch it. Delete clears a non-empty `/system` in the tombstone Update, and the data layer admits `/system` (like `/engine`) as a scoped `ServerMessageRevision` write.
- Client side: `ChatSendOptions.system` carries it through `WsClient`/`AppContext.chat.send`. A module renders it by contributing to `CHAT_CARD_EXTENSION_CONTRACT` (`shadowcat.chat-card-extension`, multi cardinality) with `ChatCardExtensionMeta { priority, match? }`; `MessageCard` renders every matching extension after its own content, higher `priority` first, ties by module id then contribution id. `match(system, message)` decides per message; absent means every message. Each extension component receives `system` and the parsed `message` engine body.

## Composer history and chat bubbles

- Composer recall: ArrowUp/ArrowDown in `Composer.svelte` walks the sent-text history and restores the draft. The list lives in the shell's session state (`getChatHistory`/`pushChatHistory`, per-world `chatHistory` key of `UiState`, exposed on `AppContext.uiState`). `@shadowcat/core`'s `pushChatHistory` bounds it by `CHAT_HISTORY_LIMIT` (50 entries) AND `CHAT_HISTORY_BYTE_BUDGET` (16 KiB of JSON): the account's whole `ui_state` blob is capped at 64 KiB server-side across every world and key, and one rejected write would also drop the panel layout and read markers riding the same patch. `parseChatHistory` turns a malformed stored value into an empty list.
- Chat bubbles (`module-chat-bubbles`) contribute `BubbleOverlay` to `STAGE_OVERLAY_CONTRACT`; a bubble appears over the speaker's token only when the token passes the render engine's applied-visibility reveal (`RenderEngine.isTokenRevealed`, fail-closed). The enable toggle is a per-device local preference (`ChatBubblesPreference`), not a world setting. The chat panel still shows every message.

## Presenting a note

`ClientMsg::PresentNote` -> `notes::handle_present_note`: GM only, spends the shared VFX bucket (`ws::VFX_RATE_PER_MIN`, the same `vfx_rate` limiter `/fx` and `PlayVfx` use), the note must be a `note` of this room's world and have `permissions.default` above `DocRole::None` (`PresentNoteError::NotShared` otherwise), then `Room::broadcast_aux(ServerMsg::PresentNote)`. The broadcast reaches around nothing: a recipient who still cannot read the note fails to open it. The client side is `WsClient`/`WorldSession` `presentNote`, `AppContext.notes.present`, the shell's presented-note handler in `Table.svelte` and the note sheet's Present button.

## Roll errors that name new dice features

`RollError::InvalidClamp { min, max }` (from `chat::rolls`' pre-roll validation, a clamp whose min floor exceeds its max ceiling) and `RollError::BestOfRequiresTotal` (a `best(...)` call in any non-Total mode, detected by `walk_groups`' best-of flag over every branch) surface as System notices like every other `RollError`. The dice semantics live in `shadowcat-codebase-dice`.
