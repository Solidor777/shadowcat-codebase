# Documents and permissions: placement rules, ingress validators and redaction seams added by newer engine types

Read this before adding an engine doc type with a parent rule, before changing `validate_containment`, the folder-delete path, `RenderHint`/`RegionEngine` validation, the embedded-copy identity pointers, or a second consumer of `filter_properties`.

## Placement rules (no database)

`data::validation::validate_containment` is the database-free placement rule: a `combat` is never parented; a `combatant`, `combat-history` and `combatant-group` always carry a `parent_id` (the persistence chokepoint `check_parent_placement` then loads the parent, including one Created earlier in the same batch via the batch's Created combats, and requires `doc_type == combat` in the same world); `combat`, the combat children, `asset_folder`, `table_folder`, `table` and `note` are never embedded, recursively through every embedded descendant. A new engine type with a parent or embedding rule adds an arm here AND an arm in the chokepoint.

## Table folders

- `TABLE_FOLDER_DOC_TYPE` (`"table_folder"`, `TableFolderEngine`) is a tree node. A `table` or another `table_folder` may carry a `parent_id`, which must name a `table_folder` of the same scope: `SqliteRepository::check_table_folder_parent`, called from `check_parent_placement` with the batch's own Created folders consulted before the database (the same batch-then-database order as `check_note_parent`).
- Deleting a folder never deletes the tables filed under it. `table_folder_reparent_moves` emits explicit `Operation::Move` ops lifting every `table` in the folder's subtree to the nearest ancestor the same command does NOT also delete (`deleted_ids` is the doomed set), so an outer-then-nested or nested-then-outer delete order lands the tables on the same surviving ancestor. Both authoritative loops (`apply_command`, `apply_intent`) call it at the start of a `Delete`'s expansion. The moves are real ops so they are logged, broadcast and invertible; a silent column update would leave every client store on the old parent. `moved_ids` feeds the `kept` argument of `descendants_first` so the expansion does not delete what was just lifted.

## Ingress validators with value rules

- `RenderHint` (a `VisionMode.render_hint`): an internally tagged enum on `kind` (`desaturate`, a colour wash with `color` and `opacity`, `outline { color }`, `none`, `custom { treatment, params }`; the custom name field is `treatment` because `kind` is the tag). The `vision-modes` document's ingress calls `RenderHint::validate` for each mode: a css `#rrggbb` colour, a finite colour-wash opacity within `0.0..=1.0`, a `treatment` of 1..=`MAX_RENDER_TREATMENT_CHARS` characters and `params` serializing within `MAX_SYSTEM_BYTES` (refused, never truncated), through `VisionMode::validate`. Unit variants are still objects on the wire (`{"kind":"desaturate"}`).
- `RegionEngine::validate` (in `data::engine::geometry`) rejects any non-finite shape coordinate besides its structural, trigger and `ambient_override` rules; the structural shape check is the same `regions::parse_region_shape` dispatch the read side uses, so ingress and read cannot drift.
- `BarAttribute` lists (`TokenOverrides.bars`, `ActorEngine.bars`, plus the optional `nameplate_mode`): `data::engine::bars::validate_bars` refuses more than `MAX_BAR_ATTRIBUTES` (4) bars and runs `BarAttribute::validate` on each (label bound, hex colour, `Formula::validate`). A token's `bars` and `nameplate_mode` REPLACE the actor's wholesale (the override wins as a unit; absent inherits). Bars are owner-writable; their secrecy is enforced at egress, not by write authority.

## Second consumers of `filter_properties`

- The `"bars"` derived channel (`scene::bars`) evaluates formulas against a host document it has first run through `filter_properties` for the recipient, so a leaf the recipient cannot read evaluates as absent and its bar is omitted; `Access::can_see` at the `OwnerOrGm` tier then decides per bar via `BarDisplayMode::delivered_to`. Any new server-side evaluator that reads document content on behalf of a recipient redacts first, then evaluates; evaluating the unredacted host and filtering the result leaks through the formula.
- Whether a nameplate mode reaches a recipient is itself gated: `TokenBars.nameplate_mode` is present only when the mode delivers to that recipient.

## Embedded actor copies of a secret-identity token

An instanced token carries its actor as an embedded copy, so withholding the token's own `actor_id` is not enough. `identity_hidden_pointers` adds, for every `/embedded/actor/<i>` copy, the `IDENTITY_HIDDEN_COPY_POINTERS` (`/name`, `/engine/displayName`, `/engine/visual`, `/engine/faction`) at `OwnerOrGm`; the copy's size, shape, conditions, light, vision and movement stay readable because footprint, rendering and the movement gate read them for every viewer. This works because `redaction_target` classifies an `/embedded/<coll>/<numeric idx>/...` pointer by what it names inside that child (a child's `/name` is a `Band`, a path into its bands is `Within`) and `redact_pointers` descends the same hops. A pointer naming a whole collection or a whole child, or a structural envelope field of a child, is refused, which is also why a child's `sourceId` stays visible. `validate_property_overrides` accepts embedded keys, while `cap::EDIT_PERMISSIONS` still gates who may write overrides. The write side of the same flag is the GM-only pair `gm_only_field_touched`/`gm_only_field_in_body` (an owner cannot toggle `identity_hidden`, and a token Create may not carry it unless the author is the GM).
