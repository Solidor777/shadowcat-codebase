# Token and actor fields: bars, facing, identity, art, overlays, quick edit

Field-level seams added to `ActorEngine`, `TokenOverrides` and `TokenEngine`, and the editor controls that write them. Read it before adding a token or actor field, an override editor or a token control.

## Override rules shared by every field below

- A linked token overrides an actor field through `TokenOverrides`; the override replaces the actor's whole object for that field (editors write the whole object), and `null` means inherit. Instanced tokens have no overrides: the editor writes the embedded actor copy.
- Validate a field in both places it can enter (the actor body and the token/override body) and keep the two validators equal; `TokenEngine::validate` and the engine-body validators are the server decider, the client `is*`/`resolve*` helpers are advisory mirrors that fail closed to the neutral value.
- GM-only fields: add the field to `gm_only_field_touched` (one list, see `shadowcat-codebase-documents-permissions`) AND make the UI control GM-only. The `TemplateMerge` path applies the same list.

## Fields

- **Bars**: `bars` (`BarAttribute`, at most four) and `nameplate_mode` on the actor and as whole-object token overrides. Owner-writable on purpose: the recipient's redacted copy bounds what any bar can show (see references/client-token-bars-art-camera-and-dash.md in `shadowcat-codebase-scene-rendering`). Editors in the `actors` module: `BarModeSelect`, `BarsEditor`, `TokenBarsControl`; bar formulas use the shared `coerceFormula`.
- **Facing vision**: `FacingVision {arc, near}` on actor, token and overrides; `resolveTokenFacingVision` is the single client resolution (`EffectiveActor.facingVision`); the server twin is `SceneEcs::resolve_token_actor_field`. Controls: `FacingVisionControl` (actor rows and create), `TokenFacingVisionControl` (GM only; linked tokens write the whole override, actorless tokens the engine, instanced tokens none). The facing switch and turn rule are scene settings (`resolveSceneSettings` `facingVision`, `facingTurnRule`); a new setting path also needs a `resolveSettingProvenance` case.
- **Rotation**: `TokenEngine.lock_rotation` (GM-write-only). A locked token refuses MANUAL rotation writes as well as auto-rotate (`lock_refusal`). `TokenRotationLockControl` lives in `ActorsPanel`. Auto-rotation and the turn rule are in `shadowcat-codebase-scene-rendering`.
- **Disposition and identity**: `TokenOverrides.disposition` is an `Option<FactionStance>`; `EffectiveActor.disposition` resolves override, then the actor's faction stance, then neutral, with one faction lookup. A TOKEN has no faction field. `TokenEngine.identity_hidden` hides identity from non-owners: the server redacts through `identity_hidden_pointers`, covering `/name`, the visual, the overrides' name/visual/disposition and `actor_id`, plus the identity fields of each EMBEDDED actor copy on an instanced token (`redaction_target` accepts embedded hops). Non-owners get no actor join, so `resolveTokenActor` and the client builders must tolerate absent copy identity fields. Controls: `TokenDispositionControl` (linked tokens only), `TokenIdentityHiddenControl` (GM only).
- **Art transform**: `VisualTransform {anchor, scale, tint, facing}` on image and animated visuals; `isValidTransform` fails closed; `TransformState` is the editor state in `VisualKindEditor` (Art framing available on every slot). Numeric inputs use step "any" so a typed decimal is not rejected by the browser. The `facing` validator must match the server's.
- **Random art pool**: `TokenVisual` can be a random-variant pool filtered by `TokenArtFilter` (asset tags, folder). A pool is resolved at token Create AND token Update (`resolve_token_random_variants`, on the transaction connection; `pick_pool_asset` is a streamed reservoir pick, Algorithm R of size 1, so memory stays one id however large the pool, and it draws with `entropy_seed`): each per-token slot gets its own draw, and a linked token draws into its own `overrides.visual` (on Update only when that write touched `overrides.visual`, so an edit that never touched art does not redraw). A concrete override suppresses the linked draw, an empty pool uses the fallback, and a pool as its own fallback is refused. Every image the server draws carries `TokenVisual::Image::drawn` (an empty-pool fallback image too). An actor Update that writes `/engine/visual` as a pool redraws every linked token through `SqliteRepository::redraw_linked_token_art`, which rewrites only a token whose `overrides.visual` is absent or `drawn`; hand-set art (`drawn` false, or another visual kind) is kept. `drawn` is not stripped from a client write: a client-sent `drawn: true` only makes that token's own art redrawable. A token Update whose write overlaps `/engine/overrides/visual` (a whole `/engine` write included) draws for a linked pool actor when the written token has no concrete override visual. Asset search shares `asset_query_builder` with `query_assets` (see `shadowcat-codebase-assets`). `TagChips` is a `ui-kit` component.
- **Conditions**: `Condition.overlay` (serde default false; the seeded dead and unconscious entries are true) feeds `ConditionDisplayEntry.overlay`; `ConditionsPanel` has the toggle. `ConditionTogglePalette` is the shared `ui-kit` chip palette (also used by quick edit); active/mixed display and click direction use the one `editableTargets()` set.
- **Carried light**: `LightEmissionEditor` takes a `carriedByToken` prop (it shows the follow-token control only for a token-carried light); every mount must pass it.

## Quick edit and delete

- `TokenQuickEdit` (`actors` module, `quickEditTokenId` = exactly one selected token): elevation, `ConditionTogglePalette`, bar nudges through `barQuickEdit` / `resolveQuickBars`. Linked tokens write `/system/<path>`, instanced tokens `/embedded/actor/0/system/<path>`. Bar label, colour and mode match greedily; writes carry the old value as the OCC pre-image.
- The Delete button is gated on `ctx.canDelete` alone and deletes with the FULL pre-image. `canDelete` is true for the GM and for the token's effective owner (the effective owner holds DELETE of the token; see the token-ownership invariant in SKILL.md). A UI that hides Delete from owners is a defect.
- A token built by `buildTokenDoc` (the place tool's output) carries `owner: null`. A LINKED token's effective owner is its actor's `/owner` (see the token-ownership invariant in SKILL.md), so a freshly placed token has no owner of its own and no player holds it until the actor is assigned one.
- Onboarding anchors (`tourAnchor`) are placed on controls here; see `shadowcat-codebase-client-shell`.
